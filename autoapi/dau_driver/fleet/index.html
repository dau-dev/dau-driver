dau_driver.fleet.run_scan_batches_fleet(devices, batches: collections.abc.Iterable[dau_driver.scan_execution.ScanBatch], *, per_key_state: bool, input_regions: tuple[int, int], row_bytes: int, collect: collections.abc.Callable[[Any], Any], timeout_seconds: float = 60.0, progress=None, weights: collections.abc.Sequence[float] | None = None, poll_yield_seconds: float | None = None) → list[FleetScanResult][source]¶

Run one independent scan pipeline per device over a shared lazy input.

Each batch is pulled exactly once by whichever device pipeline demands it. With weights=None this is pure demand-driven scheduling and naturally self-balances by device throughput. Weights use weighted round-robin only to pre-bias each shared pull toward the requested relative device shares; batches remain lazy and are never partitioned or queued ahead.

Results are returned in global batch order as frozen FleetScanResult records. Each record retains the exact device object so the caller can recover which card produced its collect value. input_regions is reused as device-local addresses, never shared memory.

per_key_state is required and must be False. A stateful composition cannot run on a fleet at all: batches are pulled from ONE shared source by whichever device is free, so a given key’s rows land on whichever cards happen to be idle and per-key state is split across devices that never see each other’s rows. Key-partitioning the input does not help — the affinity would have to be device-wide, and demand-driven scheduling is what makes the fleet self-balancing in the first place. Refusing is the same guard run_scan_batches applies to position-sliced batches, one level up.

poll_yield_seconds is passed through to each pipeline’s JOB_STATUS poll and defaults to None (spin). The real transports release the GIL in their register read (os.pread on Linux, ctypes on macOS), so concurrent pipelines interleave without it and a sleep would only add latency per poll. It exists for a pure-Python transport — a fake in a concurrent test — where the spin WOULD hold the GIL and flatten self-balancing toward an even split regardless of device speed (on fakes with a large speed gap the spinning split was close to even and took twice as long).

Known limitation: cancelling on a device failure wakes pipelines blocked pulling a batch, but one already inside its JOB_STATUS wait runs to its own completion or timeout first, so an early failure can surface only after its peers finish.

An empty batch iterable returns []. An empty device sequence raises ValueError because no pipeline can consume even a potentially lazy iterable. A single device invokes the same run_scan_batches pipeline as the multi-device workers and adds only ordered provenance records.
