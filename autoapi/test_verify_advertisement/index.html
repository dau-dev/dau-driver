test_verify_advertisement.test_a_contract_that_advertises_nothing_is_refused() → None¶

All-zero is exactly what a dead or undecoded aperture reads back as, because the driver normalizes all-ones to zero. A contract of all zeros would therefore MATCH a board that is not answering, which is the failure this module exists to prevent.

test_verify_advertisement.test_a_zero_device_word_means_not_advertised_not_zero() → None¶

Fixed binding tops place no NoC lane block, so they advertise LANE_COUNT 0 while their manifest records 1. dau’s build_tasks states the merge rule: let the manifest win over a 0 word, never the reverse. Treating it as a mismatch failed a correctly programmed board, and because the verify runs before the deadman disarm, that rebooted the host.

test_verify_advertisement.test_a_dead_board_is_caught_by_the_required_identity_not_by_the_words() → None¶

The consequence of the rule above: a board answering nothing at all now looks the same as a top that advertises nothing, so the WORDS can no longer catch it. The build identity is what does – which is why the flash path requires one.

test_verify_advertisement.test_an_unreadable_word_is_a_mismatch_not_a_skip_and_never_raises(bad) → None¶

Fail CLOSED. A word the manifest records in a form this cannot read is not the same as one it does not record: reading it as absent is how a check silently stops checking. Raising is worse still – this runs before the deadman disarm, so an uncaught exception reboots the host.

test_verify_advertisement.test_a_float_lane_count_does_not_pass_a_mismatched_device() → None¶

The concrete fail-open case: 4.0 parsed as ‘absent’ let a device advertising 1 pass a manifest expecting 4.

The incident’s own pair: q19-scan and q19-packed-wide advertise identical lane count, operator bitmap, host-opcode bitmap and sort capacity, so a word-level check passes when the board is running the other one. BUILD_ID does not.

test_verify_advertisement.test_a_board_built_under_a_superseded_palette_still_verifies(tmp_path: pathlib.Path) → None¶

Verification is registry-INDEPENDENT, and it has to stay that way.

A design flashed before a tile rename records a manifest naming tiles the palette no longer carries, under a superseded canonical-form version. The design cache refuses such an entry — it cannot re-express that spec as one it could build today — but this check asks a different question: is the board running the design THIS manifest describes. Both sides of that comparison are recorded facts, so the answer does not depend on which names the registry happens to carry now, and a resident board must not become unidentifiable because the vocabulary moved on.

The manifest is a build’s immutable record. Reading it here needs no palette and must never acquire one.

test_verify_advertisement.test_an_unstamped_shell_does_not_fail_the_exact_check() → None¶

Every shell built before stamping existed advertises 0. That is a weaker verification, not a failing one – main() says so on stderr.

test_verify_advertisement.test_a_manifest_without_a_spec_hash_does_not_fail_the_exact_check() → None¶
test_verify_advertisement.test_the_snapshot_actually_reads_build_id_back_from_the_registers() → None¶

Without this the exact check is decorative: build_id would sit at its dataclass default of 0 forever, every verification would silently fall back to the capability words, and the fallback note would be the only hint. The word ORDER matters as much – low at 0x0014, high at 0x0018, per the identity block – because a swap makes the check fail on a correctly flashed board.
